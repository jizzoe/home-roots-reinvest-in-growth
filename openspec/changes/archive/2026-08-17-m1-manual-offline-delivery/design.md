## Decisions

### Use a distinct central delivery envelope

`m1-manual-offline-delivery` is the central change for the M1 phase-1 implementation outcome. It cites the accepted `prototype-manual-offline-transaction` living specification and its archived planning change, but has its own lifecycle and completion state.

Alternative considered: reopen the archived planning change. Rejected because its historic verification is accurate and planning-only; revising it would blur what was accepted then with new component delivery.

### One mobile component change and one central linkage ledger

The future mobile repository will create one component-local OpenSpec change for its iterative implementation tasks. At central Gate 1, the central branch must be pushed and `linkage.md` initialized with the required `Contract pin`, `Dispatch`, `Returns`, `End-to-end verification`, and `Residual gaps` sections. The central change remains open while the component lifecycle runs.

Alternative considered: split mobile tasks into several central or component change packages. Rejected because the slice needs one independently reviewable, end-to-end outcome and one return record.

### Android system acceptance is assigned and scoped

Joe Rice will run system acceptance using synthetic data against an EAS internal-distribution APK produced from the returned component revision. The evidence record will be `ai-planning/evidence/m1-manual-offline-e2e.md`. Gate 1 is deliberately blocked until the mobile repository/remote is resolvable and the Android build path is executable. The representative device is a U656AC on Android 15; iOS/TestFlight is deferred.

Alternative considered: treat automated component checks as end-to-end evidence. Rejected because they do not prove an installed physical-device workflow or M1's assembled acceptance criteria.

### Use the approved prototype delivery profile

The component must provide its deterministic local checks, exact-head CI when configured, and current synthetic-only evidence. The bounded controller uses the standard `strict-first-degraded` prototype preset; no isolated independent reviewer is required by `prototype-rapid`.

Alternative considered: retain `production-rapid` and `strict-only`. Rejected because the owner selected `prototype-rapid` for this synthetic prototype and deferred the associated isolated-review gate.

## Risks / Trade-offs

- [The component checkout or remote remains absent] → Keep Gate 1 blocked; do not create a local-only handoff pin or infer a remote.
- [Android device/build is unavailable] → Keep end-to-end acceptance pending and do not claim the physical-device requirement is covered by emulators.
- [APK artifact access is broader than named prototype testers] → Pause distribution and correct the EAS access policy before sharing a build.
- [AWS or other cloud provider is requested] → Stop and route the expansion to a separately approved M1.2 change.
- [A component diverges from the accepted contract] → Request a central contract amendment, re-pin the component, and record the amendment history in the ledger.
