## Platform decisions, recorded 2026-09-06

The four blocking questions this handoff originally listed are largely answered.
The owner directed that M1.2 follow the pattern already proven in the
`jra-sonarqube` repository at
`/Users/joerice/git/joericearchitect/jra-sonarqube` rather than design a new one:

- **Same AWS account and region** as that project — no new account, no
  Organizations change.
- **Same Route 53 registered domain and hosted zone**, with a new subdomain for
  the development API.
- **ECS on EC2 instead of EKS**, on cost. Fargate was evaluated and rejected
  on 2026-09-06: it cannot hold a stable public address, so its ingress needs a
  load balancer or a TLS sidecar, and the milestone should not establish a novel
  platform path while proving an integration path. EKS remains the long-term target, so
  migration enablement is a design constraint on this milestone rather than
  future work.
- **Cost alarms and active cost control** — spin-up/spin-down scripts and
  cold-off by default, with PostgreSQL deployed as a container rather than RDS.
- **Terraform** for infrastructure.
- **Deployment through scripts**, with GitHub Actions explored during M1.2 and
  decided later.

That reference repository is worth reading before writing any Terraform. Its IAM
bootstrap brief already reserves `jra-mobile-backend-deploy` and
`jra-mobile-backend-task` role names for exactly this workload, and its
`docs/runbooks/` show the start/stop/recover and cost model this milestone
inherits.

Sharing an account with a live Terraform project creates three collisions the
first infrastructure slice must handle deliberately: the Route 53 hosted zone is
already a Terraform resource in the other project's state and must be consumed
through a data source rather than redeclared; the AWS credit and budget are
account-wide, so the combined ceiling has to be restated; and Terraform state
must be separated so a mistake in one project cannot destroy the other.

## Access and distribution decisions

**Named-tester authentication — a per-tester bearer token.** Issued out of band,
entered once at first launch, stored in the Android keystore, sent as
`Authorization: Bearer`, validated against a short server-side list, revocable
per person, and expiring on a fixed date. It is not an identity system; it
substitutes for the login flow that does not exist yet.

A two-legged OAuth client-credentials grant giving the app one key and secret was
considered and rejected. A native app is a public client, so a secret compiled
into an Expo build ships to every device and is readable as plain text in the
JavaScript bundle, and the grant needs a token endpoint, expiry, refresh, and a
token store for weaker assurance here. Published consumer apps authenticate the
user rather than the app, using Authorization Code with PKCE per RFC 8252. The
chosen token is on that path rather than a detour: runtime acquisition, keystore
storage, bearer transmission, server-side validation, and per-person revocation
all survive into M4 `entrepreneur-registration-login`, and only the acquisition
step changes.

Also decided: the hostname is `api-dev.joericearchitect.com`, leaving `api.`
free for the eventual production backend; and Android distribution stays as it
is — a signed APK through EAS internal distribution on the `preview` profile
with frozen signing credentials. Live sync changes nothing about how the APK is
built, signed, or installed, but the mobile slice owns four device-side changes:
the `INTERNET` permission must be verified rather than assumed; HTTPS only, with
no certificate pinning, because the development certificate is reissued each
session; the API address and tester credential must reach the app without baking
the credential into the build; and the installed build version must be
identifiable for test evidence.

Design brief: [M1.2 Live Sync and REST API Proof](../design-briefs/m1.2-live-sync-rest-api-proof.md).

## What M1 hands forward

M1.2 replaces a stub, not a design. The delivered prototype already has:

- A confirmed local transaction model with stable local IDs and client
  idempotency keys.
- A queued outbox shape with local, queued, synced, failed, and needs-review
  status language that never claims a remote system received a record.
- A configurable `SyncClient` boundary whose M1 implementation issues no HTTP.

M1.2 should replace that implementation without changing the confirmed
transaction model.

## Working method carried from this session

The M1 receipt slice failed twice. The second failure was diagnosed as an absent
stopping condition: "good enough" was never defined, so review kept finding new
variants and each patch grew the surface. The corrective now applied across the
prototype milestones is worth carrying into M1.2:

- Define measurable exit criteria before implementation, not after.
- Prefer a small number of hard invariants that are boolean and terminate over
  open-ended quality judgement.
- Prove the thin end-to-end path on real infrastructure early, before adding
  sophistication. For M1.2 that means one deployed endpoint accepting one
  confirmed synthetic transaction before anything else is built.
- Green automated tests are necessary and not sufficient. The discontinued
  receipt build passed 13 suites and 325 tests, then failed to save on a physical
  device.
- Push at every meaningful stopping point, and never work in a disposable
  directory. The first receipt implementation was lost to an unpushed clone under
  `/private/tmp`.
