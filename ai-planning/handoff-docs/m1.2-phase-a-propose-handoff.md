## What is being proposed

A central change in this planning repository that acts as an envelope for Phase A. It carries the product-level contract and authorizes work; the five Phase A slices then run as component-local changes inside it, in the service repository.

Phase A exists to reach exactly one checkpoint: **a real phone reaches `https://api-dev.joericearchitect.com/health` over HTTPS against a started session.** No sync code exists at that point. Everything Phase A deploys is deliberately too simple to fail for interesting reasons, so any failure is unambiguously a plumbing failure.

### The envelope must contain

The accepted `cross-repository-architecture` spec permits creating a component repository only when a reviewed and accepted planning change identifies five things. The proposal must therefore carry all of them explicitly, or it cannot authorize the repository:

1. **Repository role** — the backend component repository, owning the Spring Boot service, its Terraform, its lifecycle scripts, and its runbooks.
2. **Owner and location** — `joericearchitect/hrf-reinvest-to-grow-service`.
3. **Scope** — the five Phase A slices below, and nothing else.
4. **Validation expectations** — the per-slice checkpoint questions below.
5. **Creation trigger** — approval of this proposal's Gate 1.

Plus, because this is where money starts:

6. **The resource inventory** the single external-resource approval covers, named resource by resource. `terraform apply` runs unprompted while the plan matches it; a plan proposing anything outside it halts and needs a new approval.
7. **Phase A acceptance** — the checkpoint above.

## Governance shape

Two gates per phase, plus review points and checkpoints. The distinction matters and is recorded in the brief under Delivery Flow, Gates, and Checkpoints:

- **Gates** catch design problems. Two per phase: contract at the start, aggregated evidence at the end.
- **Review points** catch mechanism problems. One pre-declared yes/no question with evidence. Two in Phase A, at slices 1 and 4.
- **Checkpoints** catch reality problems. Objective pass/fail, they notify rather than ask, and **a failed checkpoint halts the phase** rather than queuing for the next gate.

Seven human decisions across ten slices. The frequency deliberately lives in the checkpoints, because the M1 receipt failure was a reality problem that no number of approvals would have caught.

## Two defects worth carrying as design input

Both were observed on 2026-09-06 in the reference project, and both are already recorded in the brief.

1. **Its `cold-stop` reported success while erroring**, so a host ran for eleven days unnoticed.
2. **Its budget could not see that**, because `IncludeCredit: true` subtracts credits before comparing, reporting $0.00 actual spend while $32 of credit burned.

Two independent safeguards failed simultaneously. That is why M1.2 requires both that every failing step propagates and that `status` reports observed reality rather than the last script's belief, *and* that budgets exclude credits so the backstop does not depend on the script being honest.

## The Terraform role — ready to create, not yet created

`hrf-platform-terraform` must exist before slice 1's first apply, because Terraform cannot create the role it assumes. The full procedure, policy documents, rationale, and verification commands are in [M1.2 Terraform Role Bootstrap](../plans/m1.2-terraform-role-bootstrap.md). It is written and validated but **has not been run**.

What a proposing session needs to know about it:

- It is created out of band by the account root or the existing `jra-platform-bootstrap` role, then assumed via `joe-rice-admin`. Root can create it but cannot assume it, mirroring how the reference project's role is trusted.
- It carries two inline policies: allows scoped to `hrf-*` resources, and a **guardrail policy of explicit denies** protecting the reference project. `ec2:*`, `ecs:*`, and `autoscaling:*` are account-wide, mirroring the proven role, so the denies are what actually bound the blast radius — no touching instances tagged `Name=jra-*`, no access to `jra-*` buckets or `sonarqube/*` secrets, no IAM user or access-key manipulation, no attaching `AdministratorAccess`, no hosted-zone deletion.
- Route 53 writes are confined to `*api-dev.joericearchitect.com`, because the hosted zone is shared and resource-level scoping alone would let this project overwrite `sonar.joericearchitect.com`.
- **One unverified condition.** The Route 53 statement uses `route53:ChangeResourceRecordSetsNormalizedRecordNames`, which has not been tested against the account. If slice 5 fails with an access-denied error on the DNS update, remove that `Condition` block; the zone-level scoping still holds.
- **Slice 1 owns two follow-ups**: relocating the three policy documents into the service repository under `iac/bootstrap/` as the durable record, and capturing the two `simulate-principal-policy` results named in the bootstrap plan as evidence that the guardrail actually denies and the allows actually allow.

## Working method to carry

From the M1 receipt failure, which was diagnosed as an absent stopping condition:

- Define measurable exit criteria before implementation, not after. Each slice's checkpoint question is that criterion and is already written.
- Prefer a few hard boolean invariants over open-ended quality judgement.
- Green automated tests are necessary and not sufficient. The discontinued receipt build passed 13 suites and 325 tests, then failed to save on a physical device.
- Push at every meaningful stopping point. Never work in a disposable directory.
- One slice at a time.
