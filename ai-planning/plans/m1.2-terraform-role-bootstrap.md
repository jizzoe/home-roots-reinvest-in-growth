# M1.2 Terraform Role Bootstrap

Date: 2026-09-06
Purpose: Create the `hrf-platform-terraform` role that M1.2 Phase A runs as.
Status: Executed 2026-09-06. The role exists and its guardrails are verified
against the live account; see
[M1.2 Terraform role bootstrap verification](../evidence/m1.2/m1.2-terraform-role-bootstrap-verification.md).
Relocated to the service repository at slice 1.

## Why this exists before anything else

Terraform cannot create the role it assumes. The role must therefore be created
out of band, once, by an identity that can write IAM — the account root, or the
existing temporary `jra-platform-bootstrap` role — before slice 1's first apply.

The reference project's `jra-platform-terraform` role is deliberately not reused.
Its inline policy is scoped to that project's resource inventory by name
(`jra-sonarqube-*`, `sonarqube/*`, `role/jra-*`), so it grants nothing useful
here and widening it would couple the two projects' blast radius.

## Where this file belongs

This is a planning record of a one-time bootstrap procedure. The planning
repository does not own infrastructure code, so **slice 1
(`prototype-development-terraform-bootstrap`) commits these policy documents to
the service repository under `iac/bootstrap/`** as the durable record of how the
role was created and what it was scoped to, and this file then references that
location rather than carrying the content.

## Design

The policy mirrors the structure of the reference project's proven
`jra-platform-terraform` inline policy, with four deliberate differences.

- **Everything is name-scoped to `hrf-`**, following the naming convention
  recorded in the design brief, so the two projects sharing the account are
  separable by IAM as well as by cost attribution.
- **ECR gains create and push permissions.** The reference role only pulls,
  because it runs a published upstream image. M1.2 builds and publishes its own.
- **Route 53 writes are confined to this project's hostname.** The hosted zone is
  shared with the reference project, so resource-level scoping alone would allow
  this role to overwrite `sonar.joericearchitect.com`.
- **A separate guardrail policy denies access to the other project.** This is the
  part that matters most. `ec2:*`, `ecs:*`, and `autoscaling:*` are granted
  account-wide, mirroring the reference role, because enumerating the individual
  actions Terraform needs across those services is long and churns constantly. An
  explicit deny is a harder and more legible boundary than a narrower allow.

### What the guardrail policy prevents

- Terminating, stopping, or modifying any instance tagged `Name=jra-*`, which is
  the reference project's host.
- Touching autoscaling groups, ECS clusters, or services named `jra-*`.
- Any access at all to `jra-*` buckets, `jra-*` tables, or `sonarqube/*` secrets,
  which places the other project's Terraform state out of reach.
- Modifying `jra-*` IAM roles.
- Creating or modifying IAM users, access keys, or login profiles.
- Attaching `AdministratorAccess`, `IAMFullAccess`, or `PowerUserAccess`.
- Creating or deleting hosted zones, or touching domain registration.
- Any Organizations, account, or billing change.

### Deliberately not included

GitHub OIDC federation, which belongs to M1.4. Load-balancer permissions, since
the design uses an Elastic IP and a host TLS proxy. RDS, since PostgreSQL runs as
a container. EKS, which is M2.

## Known caveat

The Route 53 statement uses the condition key
`route53:ChangeResourceRecordSetsNormalizedRecordNames` to confine record writes
to `*api-dev.joericearchitect.com`, which also covers the `_acme-challenge`
records a DNS-01 certificate challenge creates. This condition has not been
verified against the account.

**If slice 5 fails with an access-denied error on the DNS update, remove the
`Condition` block from the `Route53OwnRecordsOnly` statement.** The resource-level
scoping to the single hosted zone still applies without it, and the guardrail
policy still prevents deleting the zone.

## Procedure

Run once, as the account root or `jra-platform-bootstrap`. Re-running updates the
policies in place.

```bash
ACCT=389633344341
ROLE=hrf-platform-terraform

# 1. Create the role, or update its trust policy if it already exists
if aws iam get-role --role-name "$ROLE" >/dev/null 2>&1; then
  aws iam update-assume-role-policy --role-name "$ROLE" \
    --policy-document file://trust.json
else
  aws iam create-role --role-name "$ROLE" \
    --description "Least-privilege Terraform role for the HRF Reinvest-to-Grow prototype (M1.2)" \
    --max-session-duration 3600 \
    --assume-role-policy-document file://trust.json \
    --tags Key=Project,Value=hrf-reinvest-to-grow Key=Milestone,Value=M1.2
fi

# 2. The allow policy
aws iam put-role-policy --role-name "$ROLE" \
  --policy-name hrf-platform-terraform \
  --policy-document file://allow.json

# 3. The guardrail deny policy
aws iam put-role-policy --role-name "$ROLE" \
  --policy-name hrf-shared-account-guardrails \
  --policy-document file://guardrails.json
```

## Verification

The guardrail is testable before it is trusted. This must return `explicitDeny`:

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::389633344341:role/hrf-platform-terraform \
  --action-names ec2:TerminateInstances \
  --resource-arns arn:aws:ec2:us-east-1:389633344341:instance/i-0b1e7dc3bdb4b7d05 \
  --context-entries 'ContextKeyName=ec2:ResourceTag/Name,ContextKeyType=string,ContextKeyValues=jra-sonarqube-host' \
  --query 'EvaluationResults[].EvalDecision'
```

**The `--context-entries` argument is load-bearing and must not be dropped.** The
`ProtectOtherProjectInstances` deny is conditioned on `ec2:ResourceTag/Name`, and
`simulate-principal-policy` does not read a real resource's tags — it evaluates
only the context it is handed. Without that argument the simulation returns
`allowed`, because `ec2:*` is granted account-wide and the condition never
matches. That is a false pass reporting the absence of the guardrail, not its
presence. This was observed on 2026-09-06 against the created role.

The tag value must be a real tag on the instance named in `--resource-arns`.
Confirm it rather than assuming it:

```bash
aws ec2 describe-instances --instance-ids i-0b1e7dc3bdb4b7d05 \
  --query 'Reservations[].Instances[].Tags[?Key==`Name`].Value' --output text
```

The tag-independent denies need no context and are worth checking too, because
they exercise the guardrail statements that protect the other project's state
and secrets. All four must return `explicitDeny`:

```bash
for spec in \
  's3:GetObject|arn:aws:s3:::jra-sonarqube-terraform-state/x' \
  'secretsmanager:GetSecretValue|arn:aws:secretsmanager:us-east-1:389633344341:secret:sonarqube/admin' \
  'iam:CreateUser|*' \
  'autoscaling:SetDesiredCapacity|arn:aws:autoscaling:us-east-1:389633344341:autoScalingGroup:abc:autoScalingGroupName/jra-sonarqube-asg'
do
  aws iam simulate-principal-policy \
    --policy-source-arn arn:aws:iam::389633344341:role/hrf-platform-terraform \
    --action-names "${spec%%|*}" --resource-arns "${spec##*|}" \
    --query 'EvaluationResults[].{A:EvalActionName,D:EvalDecision}' --output text
done
```

And this must return `allowed`:

```bash
aws iam simulate-principal-policy \
  --policy-source-arn arn:aws:iam::389633344341:role/hrf-platform-terraform \
  --action-names s3:CreateBucket \
  --resource-arns arn:aws:s3:::hrf-reinvest-to-grow-terraform-state \
  --query 'EvaluationResults[].EvalDecision'
```

The simulator is a policy-evaluation check, not proof that the assumed session
behaves. Confirm the deny against the live API as well, once the profile below
is configured. Both must fail with an explicit-deny message:

```bash
aws s3 ls s3://jra-sonarqube-terraform-state --profile hrf-platform-terraform
aws secretsmanager get-secret-value --secret-id sonarqube/admin --profile hrf-platform-terraform
```

Record all results in slice 1's evidence.

## Profile configuration

The role is trusted by `joe-rice-admin` and `jra-platform-bootstrap`, mirroring
the reference project. The account root can create the role but **cannot assume
it** — `sts:AssumeRole` fails with `Roles may not be assumed by root accounts` —
so day-to-day use goes through `joe-rice-admin`.

There is no `joe-rice-admin` profile to point at. That identity arrives through
an `aws login` session recorded as `login_session` in the `default` profile, and
`source_profile` requires static credentials. The existing `terraform` profile
exists to bridge exactly this: it re-exports the default session's credentials
through `credential_process`, which Terraform's Go SDK can consume where the
`login_session` key alone would not be read. The reference project's
`jra-platform-terraform` profile is wired the same way, so this is the proven
path rather than a new one.

```ini
# ~/.aws/config
[profile hrf-platform-terraform]
region = us-east-1
source_profile = terraform
role_arn = arn:aws:iam::389633344341:role/hrf-platform-terraform
```

The chain is `hrf-platform-terraform` -> `terraform` -> `default` ->
`joe-rice-admin`. It depends on the `default` profile holding a current
`joe-rice-admin` login session; if that session is root, or expired, every
profile downstream of it fails. Confirm before use:

```bash
aws sts get-caller-identity --profile hrf-platform-terraform --query Arn --output text
# arn:aws:sts::389633344341:assumed-role/hrf-platform-terraform/<session>
```

Note that `s3:ListAllMyBuckets` is not granted, so a bare `aws s3 ls` returns an
access-denied error under this profile. That is the intended scoping, not a
misconfiguration; Terraform does not need it, and scripts should list a named
bucket instead.
