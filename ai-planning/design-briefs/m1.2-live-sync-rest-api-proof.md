## Purpose

Prove the narrowest end-to-end path from an installed Android Business Journal prototype to one deployed Spring Boot REST API that accepts and persists a confirmed synthetic transaction.

This is an integration proof. It may pull forward the minimum backend, Terraform, and deployment work needed for live sync, but it does not replace the full M2 infrastructure foundation or M3 deployment foundation.

## Product Outcome

An authorized tester can:

- install a signed, versioned Android prototype on a representative physical device;
- record and confirm a synthetic sale or expense while offline;
- see the transaction survive app restart as a local SQLite record;
- reconnect to the network;
- sync the queued transaction through authenticated HTTPS to one Spring Boot REST API;
- see the item marked `synced` only after the server durably accepts it; and
- retry safely without creating duplicate server records.

### M1.2-specific deltas from the reference

The reference deploys a third-party product for one human user through a browser. M1.2 deploys a first-party API consumed by a mobile client. That changes four things.

- **No Elasticsearch constraint, but EC2 is confirmed anyway.** The reference rejected Fargate solely because SonarQube's embedded Elasticsearch needs host-level `vm.max_map_count` and file-descriptor tuning, which a Spring Boot API does not. Fargate was therefore reconsidered on its merits and rejected on 2026-09-06; see [Why EC2 rather than Fargate](#why-ec2-rather-than-fargate).
- **Cold start is not free to the tester.** The reference accepts a 15–30 minute cold start because one person schedules their own session. M1.2's cold start gates a scripted device run, so the environment must be started deliberately before a test session and the start duration must be measured and recorded.
- **The client is a distributed retry engine, not a browser.** Cold-off means the API is normally absent. That is not a defect for M1.2; it is a free source of the controlled-outage evidence the acceptance criteria already require. See [Cost Control and the Cold-Off Lifecycle](#cost-control-and-the-cold-off-lifecycle).
- **Container images are first-party.** The reference pins a published upstream image. M1.2 must build, publish, and pin its own immutable image digest, which adds ECR and a build path the reference does not have.

### Why EC2 rather than Fargate

Owner decision, 2026-09-06. Fargate was evaluated properly rather than dismissed, because the reference project's reason for avoiding it does not apply here.

What was checked:

- **PostgreSQL runs on Fargate.** Ephemeral task storage is 20 GiB by default and up to 200 GiB, EFS is available, and ECS-managed EBS volumes are supported on Fargate platform 1.4.0 or later. Storage was not the obstacle.
- **EBS on Fargate would not have given durability anyway.** ECS documents that volumes attached to tasks managed by a *service* are never preserved and are always deleted on task termination. Durability would still have come from the S3 dump-and-restore path, exactly as it does on EC2, so the cold-off data model is unchanged by the launch type.
- **Fargate cannot hold a stable public address.** An Elastic IP cannot be associated with a Fargate task's network interface, because those interfaces are fully managed and unmodifiable. The reference project's Elastic-IP-plus-host-TLS-proxy ingress therefore has no direct equivalent; Fargate ingress means either a load balancer, which reintroduces the fixed cost this design exists to avoid, or a per-session public task IP with a TLS sidecar container.
- **Fargate would have removed real operational surface.** No AMI, no user data, no autoscaling group, no capacity provider — and with them both recovery scenarios the reference runbook records, "task stuck `PENDING` after start" and "host stuck in `Terminating:Wait` on stop".

The decision is EC2 despite that last point. The milestone's purpose is to prove an integration path, and its budget should be spent on that rather than on establishing a novel platform path, a TLS sidecar, and an in-task restore sequence at the same time. EC2 inherits a working start/stop implementation, working runbooks, and known failure modes with documented recoveries.

Recorded for the future: if the EC2 host bootstrap proves troublesome, the fallback is Fargate with a per-session public task IP and a TLS sidecar, not Fargate with a load balancer.

### Cross-project constraints this creates

Sharing an account with an existing Terraform-managed project is not free. Three collisions must be handled explicitly by the first infrastructure slice.

- **The Route 53 hosted zone is already a Terraform resource in the other project's state.** M1.2's Terraform must consume it through a data source and create only its own subdomain records. It must never declare the zone, or the two states will fight over it.
- **The AWS budget is account-wide, and the credit is shared.** The existing project sized its cap against a shared credit balance. Adding a second workload to the same account changes that arithmetic, so M1.2 needs its own budget with its own threshold and a restated combined ceiling, not a silent second tenant under the existing alarm.
- **Terraform state must be separate.** M1.2 uses its own state bucket and lock table, or at minimum its own key and lock entry, so that a mistake in one project cannot destroy the other.

## System Shape

```text
Android prototype
  SQLite confirmed transaction
  sync_outbox item with idempotency key
  authenticated HTTPS sync client -> one configured base URL
        |
        v
api-dev subdomain (Route 53 A record, session-scoped)
        |
        v
Elastic IP :443 -> host-local TLS proxy (Let's Encrypt via Route 53 DNS-01)
        |
        v
ECS singleton task on one EC2 host
  +-- spring-boot-api container
  |     idempotent transaction sync endpoint
  |     health/readiness endpoint
  |     image pinned by ECR digest
  |     secrets injected from Secrets Manager by ARN
  |
  +-- postgres container (localhost:5432, shared task network)
        synthetic transaction store on a host bind mount

        | cold-stop: verified dump gate
        v
Encrypted S3 dumps + checksum + restore metadata (durable across sessions)
```

Terraform owns the account-scoped and durable infrastructure. Scripts own the session lifecycle: allocate, converge, verify, and destroy. The only state that survives a cold stop is the verified S3 dump, the Terraform state, and the ECR images.

## Cost Control and the Cold-Off Lifecycle

Cold-off is the primary cost control, exactly as in the reference project: nothing runs while idle, and a test session is a bounded `start` → run → `cold-stop` cycle.

- The durable floor is the S3 dumps and state, the ECR images, and CloudWatch logs. The hosted zone is already paid for by the existing project.
- The session cost is the EC2 host, its EBS root volume, and the Elastic IP while attached — dollars per month at realistic session counts, against tens of dollars per month for an always-on host and materially more for an idle EKS control plane plus RDS instance.
- `cold-stop` refuses to destroy anything until a verified database dump exists in S3. This is what makes destroying the runtime safe.
- A budget alarm is a backstop, not the control. It reports overspend after the fact; the cold-off discipline is what prevents it.

Two consequences this milestone must plan for rather than discover:

- **Persistence evidence is session-scoped.** The acceptance criterion "the API durably stores the synthetic transaction in PostgreSQL" is proved by read-back within the running session, plus the verified dump captured at cold stop. A restore-and-read-back across a full stop/start cycle is a stronger and cheap addition, and is worth including once rather than assuming.
- **The API is absent by default, and that is useful.** The acceptance criteria already demand a controlled API outage that leaves the local record intact and retryable. `cold-stop` is that outage, and `start` is the recovery. The failure path gets exercised by the operating model itself rather than by a contrived fault injection.

## EKS Migration Enablement

ECS is a cost decision, not an architectural preference. The long-term intent is EKS, so M1.2 must not accumulate choices that have to be unwound later. Migration enablement is a design constraint on this milestone, not a future project.

What makes the workload portable:

- **The deployment unit is an immutable image digest in ECR.** Identical under ECS and EKS. Never deploy a mutable tag.
- **The API is a plain twelve-factor container.** Configuration by environment variable, secrets injected by reference, logs to stdout, no writes to the container filesystem, no ECS-specific SDK calls or metadata-endpoint dependencies in application code.
- **Health and readiness are plain HTTP endpoints.** An ECS container health check and a Kubernetes probe both consume them unchanged.
- **Resource requests, environment, secret references, ports, and probe settings live in Terraform variables**, not inline in a task definition. An ECS task definition and a Kubernetes Deployment then differ in serialization, not in content.
- **Terraform is layered** — account foundations, network, runtime, workload — so a migration replaces the runtime and workload layers and leaves the rest.
- **The mobile client knows only a base URL.** No runtime detail reaches the app, so migration is invisible to it.

What will genuinely have to change at migration, recorded now so it is not a surprise:

- The colocated PostgreSQL container is a prototype economy, not a target-state pattern. At migration it becomes RDS, or an explicitly operated StatefulSet with real storage. The API must therefore reach it by a configurable host and port, never by an assumption that it is on `localhost`.
- The Elastic IP plus host-local TLS proxy is replaced by an ingress controller or an ALB with ACM. Keeping TLS termination outside the application container is what makes that a swap rather than a rewrite.
- Host-level bootstrap in EC2 user data has no equivalent. Keeping it to nothing more than cluster registration and bind-mount preparation keeps it disposable.

The migration trigger should be stated as a threshold rather than a date: sustained multi-service need, a second team, an availability requirement the singleton cannot meet, or EKS becoming a deliberate learning objective with budget attached.

## Mobile Integration Requirements

- The app must save the confirmed transaction locally before any network activity.
- The app must create or reuse a stable outbox item with a client idempotency key.
- The sync client must call only the configured development API endpoint.
- The APK must not contain AWS keys, database credentials, production endpoints, or the tester's API credential. The credential is entered once at first launch and held in the Android keystore; the API address may be configured at build time.
- The app must call HTTPS only and must not pin the server certificate, because the development certificate is reissued each session.
- The item may move to `syncing` during the call.
- The item may move to `synced` only after the API acknowledges durable acceptance.
- Retry after timeout, network loss, or app restart must reuse the idempotency key.
- Failure must preserve the local record and show a comprehensible retryable or failed state.
- Because the development environment is cold-off by default, the app must treat a completely unreachable host as an ordinary retryable state and must not degrade into a failed or error state that requires manual intervention to clear.

## API Requirements

Minimum endpoints:

- `GET /health`
- `POST /v1/prototype/transactions:sync`

The sync endpoint accepts:

- client idempotency key;
- synthetic tester or prototype user identity;
- synthetic business identifier;
- local transaction identifier;
- transaction type: sale or expense;
- amount in minor units;
- currency code;
- occurrence date;
- category or purpose label;
- optional note;
- source type and source metadata summary; and
- client timestamps.

The sync endpoint returns:

- server transaction identifier;
- accepted status;
- server accepted timestamp;
- indication that the request was newly accepted or recognized as an idempotent replay; and
- enough read-back evidence to confirm the accepted record once.

Authentication is a per-tester bearer token presented in an `Authorization` header and validated against a short server-side list, as recorded in [Decisions and Open Questions](#decisions-and-open-questions). Tokens are issued out of band, are revocable individually, and carry a fixed expiry so the mechanism cannot quietly persist past the prototype. The server authenticates the tester identity from the token rather than trusting the tester identifier in the request body.

The API must reject unauthenticated writes, malformed payloads, unsupported transaction types, missing idempotency keys, expired or revoked tokens, and non-synthetic or unapproved data paths.

The accepted `api-contract-conventions` spec additionally requires, at proposal time and not later, that the API slice state its API version and compatibility expectation, name the affected clients, and define stable machine-readable error identifiers for validation, authentication/authorization, unsupported-operation, conflict/needs-review, idempotency-conflict, availability, and unexpected-failure categories. The brief above does not yet name those categories; the sync-contract slice owns them.

## Infrastructure and Deployment Requirements

Minimum infrastructure, all Terraform-owned:

- Remote encrypted S3 state with versioning, public access blocked, and a DynamoDB lock table, separate from the existing project's state.
- One isolated development environment: VPC, one public subnet, internet gateway, and route table.
- Default-deny security groups: public inbound `443` only to the TLS proxy; the database port reachable only from the API; no SSH, agent, or database port exposed publicly.
- An ECS cluster with an EC2 capacity provider and an autoscaling group sized `min 0 / max 1 / desired 0`, with managed scaling owning the desired count.
- One task definition with the API container and the PostgreSQL container, both pinned by explicit version or digest, with health checks, awslogs configuration, and bind-mounted data directories.
- ECR repository for immutable API images, with a lifecycle policy so old images do not accumulate cost.
- Secrets Manager entries for database and API credentials, created empty by Terraform and populated out of band so no value enters state.
- The `jra-mobile-backend-deploy` and `jra-mobile-backend-task` roles, least-privilege and scoped to this workload only.
- A Route 53 `A` record for the development API subdomain, consuming the existing hosted zone through a data source.
- An IAM grant letting the host complete Route 53 DNS-01 challenges for that hostname only.
- Encrypted S3 dump bucket with public access blocked and a retention lifecycle.
- CloudWatch log group for both containers.
- A monthly budget with an email alarm, and a documented shutdown rule.

Minimum deployment:

- A repeatable container build for the API, including its deterministic unit and API-contract checks.
- Immutable image publish to ECR, deployed by digest and never by a mutable tag.
- Idempotent `start`, `deploy`, `cold-stop`, `status`, and `health` scripts, each safe to re-run, each failing loudly rather than half-converging.
- Deployment metadata recorded per run: commit SHA, image digest, task-definition revision, environment, deploy result, smoke-test result, and rollback target.
- Documented rollback to the previous image digest and task-definition revision.

## Deployment Path

Owner decision, 2026-09-06: M1.2 deploys through scripts, following the reference project's `Makefile` plus `scripts/` model. GitHub Actions is explored in this milestone and decided in a later one.

### Why scripts are right for this milestone

The environment is cold-off, single-tenant, and driven by a person who is about to run a device test. A deploy is one step inside a session that a human is already conducting. Scripts also keep the whole lifecycle in one place and in one language, which is what made the reference project's start/stop path debuggable.

### What a GitHub Actions path would require

Recorded now so the later decision is informed rather than re-researched. Durable prior research exists in the reference repository under `ai-planning/research/ci-cd/`.

The split that matters is between publishing an artifact and converging an environment. These have different natural homes.

- **Build and publish is a natural fit.** Pull-request checks — Gradle build, unit tests, API-contract checks, Terraform `fmt`/`validate`/`plan` — and a main-branch job that builds once, tags by commit SHA, pushes to ECR, and records the digest. This works on GitHub-hosted runners, needs no running environment, and delivers most of the value.
- **Deploying is awkward under cold-off.** With the service normally at `desired_count 0` and no host running, a deploy job either has to start the whole environment — provisioning an EC2 host, restoring a database, allocating an Elastic IP, and waiting on TLS, all on a schedule nobody asked for — or it has to do nothing but publish and let the next `start` pick up the newest digest. The second is the honest answer: **let CI publish immutable digests, and let the session `start` script choose which digest to converge.**

Concrete prerequisites if it is adopted:

- An IAM OIDC provider for GitHub in the account, and a trust policy on `jra-mobile-backend-deploy` whose `sub` claim is restricted to the specific repository and branch or GitHub environment. Nothing broader.
- Explicit workflow permissions, starting at `contents: read`, with `id-token: write` granted only to the job that assumes the role.
- Pinned action versions, and no path by which fork pull requests reach the deploy role.
- Runtime secrets stay in Secrets Manager. They are not copied into GitHub secrets.
- A concurrency group so two runs cannot converge the same singleton environment at once.
- Deployment evidence published as job artifacts or a job summary, so the acceptance evidence has a durable home.

Decision, 2026-09-06: **automated tests only** for M1.2. GitHub runs the test suite on pull requests, which needs no AWS connection and no credentials. Image building and publishing stay local, driven by the scripts in `prototype-image-publish-and-lifecycle-scripts`, and environment convergence stays in scripts throughout.

The rest of the continuous-integration work is deferred to **M1.4 Prototype Continuous Integration**, defined on 2026-09-06 in the [V1 Scope Map and Milestone Plan](V1%20Scope%20Map%20and%20Milestone%20Plan.md) by splitting the runtime-agnostic half out of M3. M1.4 adds pull-request Terraform checks, the GitHub-to-AWS trust relationship, digest-addressed image publishing, and durable build evidence. It depends only on M1.2 and can run in parallel with the corpus-blocked M1.1 and M1.3. It explicitly does not deploy from continuous integration: environment convergence stays in scripts for as long as the environment is cold-off, and the two halves meet at the image digest rather than at the environment.

One consequence for M1.2: because M1.4 will need a GitHub-to-AWS trust relationship, and because that is an IAM change better reviewed once than retrofitted, `prototype-development-terraform-bootstrap` should leave room for it. Provisioning the identity provider there does not commit M1.2 to using it. The provider is account-level and therefore shared with the reference project, so it must be created once and referenced by the other, in the same way the Route 53 hosted zone is.

## Security and Data Boundaries

- Use synthetic data only.
- Use named tester access only.
- Use least privilege for workload roles, database access, Terraform state access, and any future GitHub OIDC role.
- Do not log secrets, bearer tokens, database credentials, or sensitive payloads.
- Do not store credentials in Git, Terraform state, or the APK.
- Do not create production/pilot data paths.
- Keep development data disposable and recoverable from a verified dump.
- Administer the host through Session Manager only. Expose no SSH, database, or agent port.
- Keep account identifiers and secret values out of committed source, including runbooks.

## Acceptance Criteria

- A named tester installs the signed Android APK on a representative physical device.
- The tester signs in or otherwise obtains approved prototype access.
- The tester records and confirms a synthetic sale or expense while offline.
- The confirmed transaction remains visible after app restart.
- The app shows the transaction queued for sync.
- When connectivity returns, the app sends an authenticated HTTPS request to the development REST API.
- The API durably stores the synthetic transaction in PostgreSQL.
- The app marks the transaction `synced` only after the API acknowledgement.
- Replaying the same outbox item does not create a duplicate server record.
- A controlled API outage — a `cold-stop` is sufficient — preserves the local transaction and produces a retryable or failed state.
- Restoring the API with `start` lets the same queued item sync successfully.
- The synchronized transaction is still present after a full `cold-stop` and `start` cycle, proving the dump-and-restore path rather than only in-session persistence.
- Smoke-test and deployment evidence record commit SHA, image digest, task-definition revision, endpoint, and rollback target.
- Cold-start duration is measured and recorded, so the cost of a test session is known rather than assumed.
- Validation evidence confirms that no real participant data, production endpoint, long-lived AWS credential, or reusable secret is present in the app, repository, state, logs, or deployment metadata.

## Candidate SDD/OpenSpec Changes

Propose these as separate, dependency-valid changes rather than one broad implementation change. The order below is the delivery order, and it follows from the thin-end-to-end decision recorded in [Decisions and Open Questions](#decisions-and-open-questions).

### Phase A — prove the plumbing

Phase A exists to make `api-dev.joericearchitect.com` answer a health check over HTTPS from a real device, before any sync code exists. Everything it deploys is deliberately too simple to fail for interesting reasons, so any failure in this phase is unambiguously a plumbing failure.

| Order | Change | Repositories | Delivers |
| --- | --- | --- | --- |
| 1 | `prototype-development-terraform-bootstrap` | backend | Terraform state bucket and lock table, the project and account-wide budgets, the `jra-mobile-backend-deploy` and `jra-mobile-backend-task` roles, VPC and networking, and the ECR repository |
| 2 | `prototype-spring-boot-service-skeleton` | backend | A Spring Boot service exposing only `GET /health`, its container build, its unit tests, and the pull-request test workflow |
| 3 | `prototype-development-ecs-cluster-and-container-postgres` | backend | ECS cluster, autoscaling group at zero, task definition, PostgreSQL container, Secrets Manager entries, encrypted S3 dump bucket, verified-dump teardown gate, and CloudWatch logs |
| 4 | `prototype-image-publish-and-lifecycle-scripts` | backend | Image build and publish by digest, the `start`, `deploy`, `cold-stop`, `status`, and `health` scripts, and the cost and start/stop/recover runbooks |
| 5 | `prototype-development-ingress-dns-and-tls` | backend | Elastic IP lifecycle, session-scoped `A` record for the development hostname, and the host TLS proxy using Let's Encrypt DNS-01 through Route 53 |

Phase A closes on one checkpoint: a real device reaches the health endpoint over HTTPS against a started session, and a `cold-stop` returns the environment to its floor.

PostgreSQL is provisioned in Phase A even though a health-only service does not need it. It shares the task definition, and provisioning it early proves the backup, verified-dump gate, and restore path before anything depends on them.

### Phase B — build the product path

| Order | Change | Repositories | Delivers |
| --- | --- | --- | --- |
| 6 | `prototype-sync-contract-and-outbox` | central + mobile + backend | The versioned sync contract, its API version and compatibility statement, the stable machine-readable error identifiers required by `api-contract-conventions`, the executable API description owned by backend, and the mobile outbox wiring |

Authentication is delivered before the sync endpoint deliberately, so that the write endpoint is authenticated from birth rather than retrofitted. It proves itself against a trivial authenticated endpoint without waiting for the real one.

`prototype-spring-boot-service-skeleton` was split out of `prototype-spring-boot-api-and-synthetic-transaction-store` on 2026-09-06. The original single change bundled the health endpoint with the transaction store, which made the thin-end-to-end checkpoint impossible to reach: Phase A cannot deploy anything without a deployable service, and it must not deploy the sync endpoint. ## Cross-Repository Delivery

M1.2 is the first milestone whose slices span repositories. It is delivered under the flow in [`cross-repository-sdd-flow.md`](../../docs/cross-repository-sdd-flow.md), which governs the mechanics below.

### Component declaration

M1.2 involves two component repositories: **mobile**, which exists, and **backend**, which does not and requires the repository-creation approvals listed under Required Approvals Before Apply.

There is no separate infrastructure repository. This is to be reconsidered when a second codebase appears.

Because M1.2 still contains cross-repository slices, **milestone-autonomous delivery is unavailable for it**. Its slices are gated on handoffs between repositories that different sessions and potentially different people own. M1.2 runs one slice at a time.

### Slice repository split

The delivery order and per-slice repositories are in [Candidate SDD/OpenSpec Changes](#candidate-sddopenspec-changes). Seven of the ten changes are single-repository and carry no cross-repository overhead.

Three changes span repositories and therefore require a component declaration, an end-to-end verification assignment, and a linkage ledger from the moment their plan gate is approved:

| Change | Repositories | Why it spans |
| --- | --- | --- |
| `prototype-sync-contract-and-outbox` | central + mobile + backend | The accepted `api-contract-conventions` spec forbids the central planning repository from creating executable API descriptions and assigns them to backend, while the outbox behavior it constrains lives in mobile. A contract change excluding backend would leave the mobile client coding against a shape nothing publishes. |

### End-to-end verification assignment

Every cross-repository slice must name its executor, environment, and evidence location before its plan gate is approved. A slice without this assignment has no path to verification and is refused at that gate. M1.2's defaults, to be confirmed or overridden per slice:

- **Executor** — Joe Rice, by owner decision on 2026-09-06, performing the device run personally. Component slices may be self-verified by their implementer. The milestone-closing slice is executed against a written step-by-step script with evidence captured per step, so that a single-person run remains reproducible by someone else later.
- **Environment** — the signed APK on a representative physical Android device, against the deployed development REST API in a started session. Explicitly **not** an emulator, and **not** the app against a stubbed or mocked API: a run that does not exercise the real service across the real network proves nothing about the sync path this milestone exists to test.
- **Evidence location** — `ai-planning/evidence/m1.2/<slice-name>.md` in this repository, referenced from the slice's linkage ledger. The directory does not exist yet and is created by the first slice that needs it.

Where a slice genuinely cannot run end to end — for example, before any development environment is provisioned — its central verification records that as an explicit residual gap rather than substituting the sum of component evidence.

### Linkage ledger

Each cross-repository slice carries a linkage ledger at `openspec/changes/<change-id>/linkage.md` in this repository, recording the contract pin and its amendment history, a dispatch entry per component repository, each return record as components close out, the end-to-end verification assignment and result, and any residual gaps. It is the durable record that lets a slice be resumed, and it is where the evidence listed under Evidence Required Before Closing M1.2 is referenced from.

## Decisions and Open Questions

### Resolved

Recorded in [Adopted Platform Pattern](#adopted-platform-pattern) on 2026-09-06: the runtime (ECS on EC2, not EKS and not Fargate), the AWS account, the DNS approach, the database model (container, not RDS), the infrastructure-as-code tool, the cost-control model, and the deployment mechanism.

Resolved by owner decision on 2026-09-06:

- **Repository layout — one repository.** The Spring Boot API, its Terraform, its scripts, and its runbooks live together, following the reference project's pattern of keeping infrastructure beside the deployable. To be reconsidered when a second codebase appears. This reduces M1.2 from three component repositories to two: mobile, and backend-with-infrastructure.
- **Build order — thin end to end first.** Deploy an API that answers only a health check, and reach it from a real device over HTTPS, before the sync endpoint exists. Any failure in that first pass is unambiguously a plumbing failure. The API and sync contract are developed in parallel against a local PostgreSQL container using the same image the deployed task runs. This applies the working method carried from the M1 receipt failure: prove the thin path on real infrastructure early.
- **Terraform state — its own bucket and lock table**, separate from the reference project's. Versioned, encrypted, public access blocked. The cost is negligible and it keeps a mistake in one project from reaching the other.
- **Cost control — two budgets.** A project budget of $15/month for attribution, plus an account-wide budget of $33/month as the real guardrail, because both projects share one account and one credit. The account-wide figure is the one that protects the credit; the per-project figure tells you which workload spent it. Budgets beyond the first two carry a small daily charge, which is accepted. Neither alarm is the control: cold-off is.
- **End-to-end verification executor — Joe Rice**, running the final device test personally. Component slices may be self-verified. The milestone-closing slice is executed against a written step-by-step script with evidence captured per step, so the run is reproducible by someone else later.
- **Continuous integration — automated tests only.** GitHub runs the test suite on pull requests. No AWS connection, no credentials, and no deployment automation in M1.2. Image publishing is added when the API has a stable build file; environment convergence stays in scripts. See [Deployment Path](#deployment-path).
- **Development API hostname — `api-dev.joericearchitect.com`.** The personally owned apex is accepted for synthetic prototype use. `api.` is left free for the eventual production backend, since the apex is a shared personal platform that already hosts `sonar.`. The obligation to move to a Home Roots–owned domain before any participant use is recorded alongside the mobile-repository transfer obligation.
- **Named-tester authentication — a per-tester bearer token.** Issued out of band, entered once at first launch, stored in the Android keystore, sent as `Authorization: Bearer`, validated against a short server-side list, revocable per person, and expiring on a fixed date.

  It is not an identity system: no login, password, registration, recovery, or refresh. It exists precisely because no login flow exists yet, and it substitutes for one without building one.

  A two-legged OAuth client-credentials grant giving the app a single key and secret was considered and rejected. A native app is a public client, so a secret compiled into the build ships to every device and is readable from the APK — in an Expo build, as plain text in the JavaScript bundle. The grant also requires a token endpoint, expiry, refresh, and a server-side token store, making it more machinery than a static token for weaker assurance here. Published consumer apps do not authenticate the app at all; they authenticate the user with Authorization Code plus PKCE, as prescribed by RFC 8252, because PKCE substitutes a per-login proof for the client secret a native app cannot hold. Keys that genuinely do ship inside apps, such as a Maps key, are identifiers restricted by package name and signing-certificate fingerprint, not secrets, and they authorize third-party reads rather than writes to first-party data. Proving a request came from the genuine app is a separate mechanism again — hardware-backed attestation through Play Integrity or App Attest — layered on top of user authentication rather than replacing it.

  The chosen token is on the path to M4 rather than a detour. The credential is obtained at runtime, stored in the keystore, sent as a bearer token, validated server-side, and revoked per person — all of which survive into the PKCE design that M4's `entrepreneur-registration-login` will need once many entrepreneurs each own their own records. Only the acquisition step changes, from typed-in to obtained through a login flow. A client secret compiled into the build is the one option that would be discarded entirely at M4.

  Two-legged OAuth remains correct for service-to-service calls in the final architecture: a backend calling a third party, or a scheduled job calling the API, are confidential clients that can hold secrets properly.

- **Android distribution — unchanged.** M1 already ships a signed APK through EAS internal distribution on the `preview` profile with frozen Android signing credentials, and nothing in the live-sync work changes how the APK is built, signed, or installed. Re-evaluate when the tester group grows beyond people who can be handed a file directly. The mobile slice owns four device-side changes this creates: the `INTERNET` permission must be verified rather than assumed; the app calls HTTPS only, with **no certificate pinning**, because the development certificate is reissued each session; the API address and tester credential must reach the app without the credential being baked into the build; and the installed build version must be identifiable for test evidence.

## Risks

| Risk | Mitigation |
| --- | --- |
| M1.2 becomes full platform buildout | Limit scope to one API, one synthetic transaction sync path, and one cold-off development environment. EKS, RDS, ALB, and Helm are excluded outright. |
| Infrastructure work outruns product learning | Require explicit approval and cost controls before provisioning, and keep the vertical sync proof as the only slice that can close the milestone. |
| ECS choice quietly becomes a permanent architecture | Treat migration enablement as a design constraint of this milestone, not future work. See [EKS Migration Enablement](#eks-migration-enablement). |
| Shared AWS account causes cross-project damage | Separate Terraform state, consume the shared hosted zone through a data source only, and give this workload its own least-privilege roles and its own budget. |
| Colocated PostgreSQL loses data on teardown | Gate every teardown on a verified, checksummed S3 dump, and prove restore-and-read-back across a full stop/start cycle as an acceptance criterion. |
| Live API work weakens offline-first behavior | Require local durability before network activity, preserve queued retry states, and treat an unreachable host as ordinary and retryable. |
| Cold start makes test sessions expensive in time | Measure and record cold-start duration; treat it as a known session cost rather than a surprise on test day. |
| Tester auth becomes production identity | Use provisioned prototype access only; defer registration, recovery, roles, and profiles to M4. |
| Duplicate sync creates unreliable records | Require idempotency keys and replay evidence. |
| Secrets leak into app, Git, state, or logs | Create secrets empty in Terraform and populate out of band, inject by ARN reference, use least privilege, and run explicit secret-pattern review. |
| An idle environment is left running | Cold-off by default, a documented shutdown rule, a status command that reports plainly when a host is up, and a budget alarm as the backstop. |
