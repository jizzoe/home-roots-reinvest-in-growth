# M1.2 Live Sync REST API Proof Design Brief

Status: Draft for review
Milestone: M1.2 Live Sync and Prototype API Proof
Companion scope map: [V1 Scope Map and Milestone Plan](V1%20Scope%20Map%20and%20Milestone%20Plan.md)
Predecessor: [M1 Rapid Thin-Slice Prototype Brief](m1-rapid-thin-slice-prototype.md)
Foundation: [M0 SDD and Product Foundation Design Brief](m0-sdd-and-product-foundation.md)

## Purpose

Prove the narrowest end-to-end path from an installed Android Business Journal prototype to one deployed Spring Boot REST API that accepts and persists a confirmed synthetic transaction.

This is an integration proof. It may pull forward the minimum backend, Terraform, and deployment work needed for live sync, but it does not replace the full M2 infrastructure foundation or M3 deployment foundation.

## Product Outcome

An authorized tester can:

- install a signed, versioned Android prototype on a representative physical device;
- record and confirm a synthetic sale or expense while offline;
- see the transaction survive app restart as a local SQLite record;
- reconnect to the network;
- sync the queued transaction through authenticated HTTPS to one Spring Boot REST API;
- see the item marked `synced` only after the server durably accepts it; and
- retry safely without creating duplicate server records.

## Execution Mode

Recommended profile:

`prototype-integration-proof`

Constraints:

- Synthetic data only.
- Named prototype testers only.
- No participant, production, personal, operational, or sensitive data.
- No production or pilot deployment.
- No reusable AWS credentials in the mobile app or repository.
- No unauthenticated public write endpoint.
- No broad identity, admin, reporting, loan, inventory, receipt upload, speech, OCR, or AI scope.
- No multi-service architecture; one Dockerized Spring Boot modular monolith is enough.
- No OpenSpec Store configuration unless a separate approved change authorizes it.

## Required Approvals Before Apply

M1.2 cannot be applied until the product team explicitly approves:

- AWS account, development region, budget limit, cost alarm, and shutdown rule;
- root domain, hosted-zone approach, development API subdomain, and TLS ownership;
- Terraform state backend, encryption, state-access roles, and recovery expectations;
- GitHub organization/repositories, Actions OIDC trust, deploy approvers, and image provenance requirements;
- named-tester authentication approach;
- API-contract convention for transaction sync, idempotency, error responses, and read-back evidence; and
- validation plan across mobile, backend, infrastructure, deployment, and end-to-end device sync.

## Scope

### Included

- Signed/versioned Android prototype from M1.
- Local SQLite confirmed transaction and sync outbox.
- Mobile sync-client configuration for one development API base URL.
- Named-tester authentication sufficient for synthetic prototype access.
- One Spring Boot modular-monolith REST API.
- `GET /health` or equivalent health/readiness endpoint.
- One versioned transaction-sync endpoint for confirmed manual sale and expense records.
- Idempotent create behavior using a client idempotency key.
- PostgreSQL persistence for synchronized synthetic transactions.
- Read-back evidence that an acknowledged transaction was accepted once.
- Docker image build and immutable image publication.
- Development EKS runtime for one API workload, if explicitly approved.
- ECR repository for API images.
- Minimal development VPC/networking needed for the API and PostgreSQL.
- Secrets Manager for API/database secrets.
- Public HTTPS ingress for the development API.
- CloudWatch logs and explicit cost controls.
- Development-only Helm chart or equivalent workload package.
- GitHub Actions checks, build, publish, and development deploy path through narrowly scoped OIDC.
- Smoke test, deployment metadata, and rollback target.

### Excluded

- Production, staging, or pilot environments.
- Production participant data or real financial data.
- Self-registration, password recovery, staff roles, or full identity/profile workflows.
- HRF admin portal.
- Reports, exports, loans, inventory, supplier ordering, marketplace, or coaching workflows.
- Speech, text-to-speech, receipt capture, OCR, receipt upload, or AI assistance.
- Multi-service decomposition.
- GitOps/Argo CD.
- Mobile app store release beyond the approved prototype tester distribution path.
- Full M2/M3 infrastructure and deployment foundation beyond the bare minimum needed for this proof.

## System Shape

```text
Android prototype
  SQLite confirmed transaction
  sync_outbox item with idempotency key
  authenticated HTTPS sync client
        |
        v
Development HTTPS endpoint
        |
        v
Spring Boot REST API
  idempotent transaction sync endpoint
  health/readiness endpoint
        |
        v
PostgreSQL synthetic transaction store
```

Terraform owns the approved development infrastructure. GitHub Actions builds, tests, publishes, and deploys the exact API image digest to the development runtime after approved checks pass.

## Mobile Integration Requirements

- The app must save the confirmed transaction locally before any network activity.
- The app must create or reuse a stable outbox item with a client idempotency key.
- The sync client must call only the configured development API endpoint.
- The APK must not contain AWS keys, database credentials, or production endpoints.
- The item may move to `syncing` during the call.
- The item may move to `synced` only after the API acknowledges durable acceptance.
- Retry after timeout, network loss, or app restart must reuse the idempotency key.
- Failure must preserve the local record and show a comprehensible retryable or failed state.

## API Requirements

Minimum endpoints:

- `GET /health`
- `POST /v1/prototype/transactions:sync`

The sync endpoint accepts:

- client idempotency key;
- synthetic tester or prototype user identity;
- synthetic business identifier;
- local transaction identifier;
- transaction type: sale or expense;
- amount in minor units;
- currency code;
- occurrence date;
- category or purpose label;
- optional note;
- source type and source metadata summary; and
- client timestamps.

The sync endpoint returns:

- server transaction identifier;
- accepted status;
- server accepted timestamp;
- indication that the request was newly accepted or recognized as an idempotent replay; and
- enough read-back evidence to confirm the accepted record once.

The API must reject unauthenticated writes, malformed payloads, unsupported transaction types, missing idempotency keys, and non-synthetic or unapproved data paths.

## Infrastructure and Deployment Requirements

Minimum infrastructure:

- Remote encrypted Terraform state with approved access roles.
- One isolated development environment.
- Minimal VPC/networking for EKS, API ingress, and PostgreSQL.
- EKS development runtime only if explicitly approved for M1.2.
- ECR repository for immutable API images.
- PostgreSQL reachable only by the API workload.
- Secrets Manager for credentials and secret configuration.
- DNS, TLS certificate, and HTTPS ingress under an approved owned domain.
- CloudWatch logs.
- Cost budget/alarm and documented shutdown rule.

Minimum deployment:

- Pull-request checks for backend unit/API-contract behavior.
- Container image build.
- Immutable image publish to ECR.
- Development-only Helm chart or equivalent deployment package.
- GitHub OIDC role limited to the development deployment needs.
- Deployment metadata: commit SHA, image digest, chart/config version, environment, deploy result, smoke-test result, and rollback target.
- Documented rollback to the previous image digest.

## Security and Data Boundaries

- Use synthetic data only.
- Use named tester access only.
- Use least privilege for GitHub OIDC, workload roles, database access, and Terraform state access.
- Do not log secrets, bearer tokens, database credentials, or sensitive payloads.
- Do not store credentials in Git or the APK.
- Do not create production/pilot data paths.
- Keep development data disposable and recoverable.

## Acceptance Criteria

- A named tester installs the signed Android APK on a representative physical device.
- The tester signs in or otherwise obtains approved prototype access.
- The tester records and confirms a synthetic sale or expense while offline.
- The confirmed transaction remains visible after app restart.
- The app shows the transaction queued for sync.
- When connectivity returns, the app sends an authenticated HTTPS request to the development REST API.
- The API durably stores the synthetic transaction in PostgreSQL.
- The app marks the transaction `synced` only after the API acknowledgement.
- Replaying the same outbox item does not create a duplicate server record.
- A controlled API outage or failed deployment preserves the local transaction and produces a retryable or failed state.
- Restoring the API lets the same queued item sync successfully.
- Smoke-test and deployment evidence record commit SHA, image digest, deployed config version, endpoint, and rollback target.
- Validation evidence confirms that no real participant data, production endpoint, long-lived AWS credential, or reusable secret is present in the app, repository, logs, or deployment metadata.

## Risks

| Risk | Mitigation |
| --- | --- |
| M1.2 becomes full platform buildout | Limit scope to one API, one synthetic transaction sync path, and one development environment. |
| Infrastructure work outruns product learning | Require explicit approval and cost controls before provisioning. |
| Live API work weakens offline-first behavior | Require local durability before network activity and preserve queued retry states. |
| Tester auth becomes production identity | Use provisioned prototype access only; defer registration, recovery, roles, and profiles to M4. |
| Duplicate sync creates unreliable records | Require idempotency keys and replay evidence. |
| Secrets leak into app, Git, or logs | Use Secrets Manager, OIDC, least privilege, and explicit secret-pattern review. |
| EKS cost or complexity overwhelms the proof | Confirm EKS as an approved learning objective before provisioning; otherwise pause for a runtime decision. |
